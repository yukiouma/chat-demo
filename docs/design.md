# CRF Agent Demo — Design

A local desktop chat client for an LLM, backed by an HTTP service that owns user identity, conversation history, and the catalogue of available models.

This document records the decisions made during design. The domain vocabulary lives in [GLOSSARY.md](../GLOSSARY.md); the decisions that earned a permanent record live in [docs/adr/](adr/).

---

## Shape

Two processes in one Cargo workspace.

```
┌─────────────────────────────────────┐        ┌──────────────────────────────────┐
│  Tauri desktop app (src-tauri)      │        │  Axum backend (apis)             │
│                                     │        │                                  │
│  React 19 + MUI 9 + @mui/x-chat     │        │  axum 0.8 + sqlx 0.9             │
│        │                            │        │        │                         │
│        │ Tauri commands             │        │        │ sqlx                    │
│        ▼                            │        │        ▼                         │
│  Rust: rig 0.44 ──────────────┐     │        │  PostgreSQL 17                  │
│        │  HTTP Basic           │     │        │  (crf_agent_demo)               │
│        └──────────────────────┼─────┼───────▶                               │
└────────────────────────────────┼─────┼───────┘
                                 │     │
                                 │     └──── Basic auth on every request
                                 ▼
                          Ollama (localhost:11434)
                          native /api/chat
```

The React layer never talks to the backend or to Ollama directly. It talks to Rust through Tauri commands; Rust talks to both. The credential lives in Rust, never in JavaScript ([ADR-0002](adr/0002-stateless-basic-authentication.md)).

## Data model

Defined in [apis/migrations/](../apis/migrations/).

### `users`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | PK |
| `username` | `text` | unique |
| `password` | `text` | plain text — demo shortcut, see [ADR-0002](adr/0002-stateless-basic-authentication.md) |
| `created_at` | `timestamptz` | |

### `models`

| Column | Type | Notes |
|---|---|---|
| `name` | `text` | PK. The name the inference engine knows the model by, e.g. `qwen3:32b` |
| `display_name` | `text` | label for the picker |
| `supports_reasoning` | `boolean` | whether the model can produce thinking |
| `supports_tools` | `boolean` | whether the model can call tools |
| `enabled` | `boolean` | offered to users |
| `is_default` | `boolean` | pre-selected in a new conversation |

The catalogue is **static**: rows are seeded, never discovered from Ollama. The backend has no idea which models are actually pulled locally.

### `conversations`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | PK |
| `user_id` | `uuid` | FK → `users`, cascade delete |
| `title` | `text` | nullable until the first message |
| `model_name` | `text` | FK → `models.name`. Switchable mid-conversation |
| `forked_from_conversation_id` | `uuid` | FK → `conversations`, nullable |
| `forked_from_message_id` | `uuid` | FK → `messages`, added in migration 0003 |
| `created_at`, `updated_at` | `timestamptz` | `updated_at` orders the sidebar by recent activity |

### `messages`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | PK. Generated by React for user messages, by Rust for assistant messages |
| `conversation_id` | `uuid` | FK → `conversations`, cascade delete |
| `role` | `text` | `user`, `assistant` or `system` |
| `seq` | `integer` | position within the conversation; unique per conversation |
| `parts` | `jsonb` | typed parts, our vocabulary |
| `content` | `text` | denormalised plain text, for display and search |
| `status` | `text` | `sent`, `error` or `cancelled` |
| `created_at` | `timestamptz` | |

`seq` is assigned by the backend as `max(seq) + 1` within the conversation, in the same transaction as the insert. Forking copies the prefix and **preserves** the original `seq` values, so the fork's next message continues from where the source conversation had reached.

### The Instructions

A conversation's **Instructions** are stored as a message of their own, with the role `system` ([ADR-0006](adr/0006-instructions-are-a-message.md)). They are written by the application, said by nobody, and never shown in the transcript.

They sit at `seq` 0 — the head of the conversation — rather than at the end where a new message normally goes. That is what makes a fork inherit them: the fork copies every message with `seq <=` the fork point, and position zero is always below it. No fork code knows anything about them.

There is exactly one per conversation. `PUT /api/conversations/:id/instructions` owns it, and the generic message-append endpoint refuses the `system` role outright, so the rule cannot be broken from the side.

Two states that look alike are not alike:

| State | What the model runs with |
|---|---|
| No instructions message | The built-in default, which lives in the desktop app |
| An instructions message that is empty | Nothing at all |

A new conversation is seeded with the built-in default as its instructions, so it has the message from the start.

**Turns are derived, not stored.** A Turn is one user message plus the assistant message that answers it. There is no `turn_id` column, because nothing queries by it.

**One assistant message per turn.** When the model calls a tool, the call, its result and the answer that followed are all parts of one assistant message. This is not only a choice: the UI library treats a `finish` chunk as the end of the whole stream and renders one bubble per stream, so a turn that spans several messages could not be shown at all. The parts still record the order — the call comes before the answer — and rebuilding the model's context splits the message back apart at the tool (see below).

### Part vocabulary

```jsonc
{ "type": "text",     "text": "…" }
{ "type": "reasoning", "text": "…" }
{ "type": "tool", "call_id": "…", "name": "current_time",
  "input": { … }, "output": { … }, "status": "output-available" }
```

A tool's input and output live in the same part ([ADR-0003](adr/0003-jsonb-message-parts.md)). The tool's `status` mirrors the UI library's tool invocation states, so the renderer can show the call in progress, awaiting approval, or finished.

The two halves of a tool part are written by different parties: the model writes the request and the arguments, and the application writes the outcome. The part is stored in the assistant's message because the assistant's message is the turn — but the outcome was never said by the assistant, and the model is never told that it was. See the glossary's **Application** and **Tool Invocation**.

## Backend API

Every endpoint requires HTTP Basic authentication. All bodies are JSON.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/me` | Validate the credential; return the user |
| `GET` | `/api/models` | The model catalogue |
| `GET` | `/api/conversations` | The user's conversations, most recent first |
| `POST` | `/api/conversations` | Create a conversation; body `{ "model": "qwen3:32b" }` |
| `GET` | `/api/conversations/:id/messages` | The conversation's messages, in `seq` order |
| `POST` | `/api/conversations/:id/messages` | Append messages; body is an **array** of messages |
| `PUT` | `/api/conversations/:id/instructions` | Set the conversation's instructions; body `{ "instructions": "…" }` |
| `DELETE` | `/api/conversations/:id` | Delete a conversation and its messages |
| `POST` | `/api/conversations/:id/fork` | Fork; body `{ "from_message_id": "…" }`; returns the new conversation |
| `PATCH` | `/api/conversations/:id` | Change the conversation's model; body `{ "model": "…" }` |

`POST …/messages` is called twice per turn: once with `[user_message]` when the turn starts, and once with `[assistant_message]` when it completes. It refuses the `system` role: the instructions have an endpoint of their own.

Forking is a single transactional operation on the backend: create the new conversation, copy every message with `seq <=` the fork point, preserve their `seq` values, and record the lineage. The instructions are at position zero, so they come along without being named.

## Desktop command surface

The React layer reaches the backend only through these Tauri commands.

| Command | Purpose |
|---|---|
| `login(username, password)` | Validate against the backend; store the credential in Rust state; return the user |
| `list_models()` | The model catalogue |
| `list_conversations()` | The sidebar |
| `create_conversation(model)` | New conversation, seeded with the built-in instructions |
| `delete_conversation(id)` | Remove a conversation |
| `fork_conversation(id, from_message_id)` | Fork |
| `load_messages(conversation_id)` | Load a conversation into the UI |
| `update_conversation(id, model)` | Switch the model mid-conversation |
| `set_instructions(id, instructions)` | Set the conversation's instructions |
| `send_message(conversation_id, message, history, model, system_prompt, channel)` | Run the turn — see below |

`send_message` takes the conversation's messages from the client, because the client already has them ([ADR-0005](adr/0005-client-supplies-conversation-history.md)). It takes the instructions the same way, for the same reason.

The client sends a `HistoryMessage` — an id, a role and its parts — rather than a stored message. The fields the server owns (the conversation, the position, the plain text, the timestamp) are left out on purpose: the desktop never has to invent values for them, and a message it did not store cannot fail to parse. The client's id is kept when it is a UUID, so its optimistic copy and the stored message agree; when it is not, the server gives the message one of its own.

## The turn lifecycle

1. The user sends a message. The UI creates the message — including its `id` — and calls `send_message` with the conversation's full message list, the selected model, the conversation's instructions, and a Tauri `Channel`.
2. Rust persists the user message to the backend. If the app dies from here on, the user's question is not lost.
3. Rust converts the stored messages into rig's `Message` form and builds a `CompletionRequest` from the whole conversation.
4. Rust streams the agent over the `Channel` as our own chunk types.
5. On completion, Rust assembles the assistant message from the streamed chunks and persists it.
6. The UI already has the answer rendered; it reconciles the persisted ids and status.

### The preamble

The conversation's instructions are not part of the history. They go to the model as rig's preamble, which the agent puts in front of everything else as a system message — so the model sees them first, ahead of the dialogue.

There are three cases, and they are not the same:

| The conversation has | The model runs with |
|---|---|
| Its own instructions | Those |
| Instructions that are empty | Nothing |
| No instructions of its own | The built-in default, which lives in the desktop app |

The desktop app splits the instructions off the loaded messages before they reach the transcript, and passes them to `send_message` as their own argument. The backend is never asked for them: the client already holds them, the same way it holds the history ([ADR-0005](adr/0005-client-supplies-conversation-history.md)).

The user edits them in a dialog, opened from a button beside the model picker. The dialog holds the editable text and, beneath it, exactly what the model will be given — which is not always the same thing, because a conversation with no instructions of its own is running on the built-in default, and one whose instructions are empty is running on nothing.

### Rebuilding the model's context

rig wants a tool call inside an assistant message and the tool's result in a *separate* user message. Our stored message holds the call, the result and the answer that followed, as parts of one message. Converting between the two is a single function with one job: walk the parts, and when a `tool` part is met, close the assistant message there, emit rig's user message with the tool result, and carry on with the rest of the parts in a new assistant message.

The result is that the model sees exactly what it said the first time: the call, then the result, then the answer.

Four details of that conversion matter more than they look:

- **The result says whether the tool failed.** The stored part's status carries it, and the model's copy of the result carries it too. A failure the model cannot see is a failure it will build on.
- **A call that never came back still gets an answer.** A turn that is cancelled between the call and the tool's return leaves a tool part with no output. Replaying it as a bare call would leave the model holding a call nothing ever answered, which is a malformed conversation. It is paired with an error result instead.
- **A tool that answered with a string is replayed as that string**, not as its JSON encoding. The model answered with `2026-01-01T00:00:00Z`, and it should see exactly that.
- **Calls the model made at once stay together.** Two calls in one message are sent as one assistant message holding both, followed by one message per result — not interleaved.

Reasoning is **not** replayed to the model. The model does not need to see its own thinking again, and providers are not all willing to accept a message that carries it. It is kept for display only.

The instructions are not replayed either: they are the preamble.

This is the most bug-prone code in the project: a mistake here does not crash, it produces a conversation that looks plausible but is not what was stored. It has unit tests.

### The tool loop

rig's agent runtime runs the loop: it detects the model's tool call, executes the tool, feeds the result back, and calls the model again. The caller never sends a tool result back itself.

Two settings matter:

- `default_max_turns` **defaults to 1**, which means no tool round-trip ever completes. It must be raised.
- `Tool::NAME` is an associated constant, and a tool's `parameters()` returns `serde_json::Value`, not a schemars schema.

The demo defines one tool, `current_time`, and executes it without asking the user first.

## Streaming contract

Rust emits our own chunk types over a Tauri `Channel`. The TypeScript adapter maps them to the UI library's chunk types.

```jsonc
{ "type": "start",          "message_id": "…" }
{ "type": "text_delta",     "message_id": "…", "part_id": "…", "text": "…" }
{ "type": "reasoning_delta","message_id": "…", "part_id": "…", "text": "…" }
{ "type": "tool_call",      "message_id": "…", "call_id": "…", "name": "…", "input": { … } }
{ "type": "tool_result",    "message_id": "…", "call_id": "…", "name": "…", "output": { … }, "is_error": false }
{ "type": "finish",         "message_id": "…" }
{ "type": "error",          "message_id": "…", "message": "…" }
```

`part_id` names the part being written. The UI library resolves parts by that name, so a run of thinking before a tool call and the run after it have different names — and so are two parts, in the order they arrived, rather than one merged block.

There is no chunk for the tool's arguments arriving piece by piece: the call id is not known until the call is complete, so there is nothing to attach a fragment to. The arguments arrive in one piece with the call.

Two mappings live in TypeScript, and only in TypeScript:

1. **Chunk → UI library chunk.** The UI library's `ChatAdapter.sendMessage` must return a `ReadableStream` of *parsed objects*, not bytes, so the adapter decodes what Rust sends and enqueues the library's own chunk shapes. The library identifies a text or reasoning *part* rather than a message, so the adapter opens each part with a `text-start` or `reasoning-start`, closes the one before it when a new one opens, and closes the last on `finish`.
2. **Stored part → UI library part.** A row from the database becomes the library's `ChatMessagePart`.

The library supports reasoning and tool calls natively, with default renderers, and renders markdown — including fenced code blocks — out of the box. The adapter's job is to hand it the right shapes.

A failed turn arrives as an `error` chunk, which the adapter turns into a failed stream. The library then marks the message as errored and keeps whatever was generated.

### Why a `Channel` and not events

A Tauri `Channel` is per-call and ordered, which is exactly what a token stream needs. Tauri events are a global bus that would need unique names per in-flight request, and would leave cross-talk between conversations to us.

## Model catalogue

Static, seeded with one row for `qwen3:32b`. The backend does not consult Ollama, so it cannot know which models are actually pulled. If a user picks a model that is not present locally, the turn fails with an error from Ollama.

## Authentication

HTTP Basic on every request. The password is stored in plain text in `users.password` — a deliberate demo shortcut, not a design position ([ADR-0002](adr/0002-stateless-basic-authentication.md)). The backend never returns the password in a response body.

## Error handling

- **Before streaming starts** — a failed authentication, an unreachable backend, a model that is not pulled: the Tauri command rejects, the adapter throws, and the UI library's error state handles it.
- **Mid-stream** — the failure arrives as an `error` chunk. The assistant message ends with `status: 'error'` and **keeps whatever text was generated**, so a half-answer is not thrown away. The UI library renders the error state on the message.
- A turn the user cancels ends with `status: 'cancelled'`, keeping the partial content.

## Testing

**Backend integration tests**, using `sqlx::test` to give each test its own scratch database. The `yuki` role is a superuser with `CREATEDB`, so no separate test role is needed. Covered: credential rejection, conversation listing and ordering, message ordering by `seq`, fork semantics and lineage, cascade delete, one user's isolation from another's, and the instructions — setting them, replacing them, inheriting them through a fork, and the append endpoint refusing the `system` role.

**Rust unit tests** for the two functions where a bug produces a plausible-looking wrong answer rather than a crash:

- stored messages → rig messages, including the tool-call/tool-result split, a failed tool replayed as a failure, a call that never came back, a string result sent as text, and the instructions not replayed
- rig stream events → our chunks

**Two tests that need the outside world**, and are therefore ignored by default:

- `cargo test -p crf-agent-demo --test turn -- --ignored` — a turn against a local Ollama with `qwen3:32b` pulled, checking that the thinking, the tool call and the answer all arrive.
- `cargo test -p crf-agent-demo --test desktop -- --ignored` — the whole desktop path: sign in, ask, stream, keep. It needs the backend running.

## Out of scope

Agreed as out of scope: regenerating an assistant message, editing or deleting individual dialogue messages (the instructions are the exception — they are configuration, and they are editable), attachments and file parts, source-URL and source-document parts, typing indicators, more than one participant in a conversation, and realtime subscription. Renaming a conversation is deferred but is only a column and an endpoint away.

In scope: markdown and code-block rendering of assistant text.

## Dependency notes

Facts verified against the vendored crate sources, recorded here because they are easy to get wrong.

- **rig 0.44 is a breaking rewrite.** There is no `CompletionModel`, no `.build()`, and no `.prompt()` on a model. The shape is `Ollama::new().native_completion(name)` → `Model<ollama::Chat>` → `.call(request)` / `.stream(request)`.
- **Use `native_completion`, not `completion`** — see [ADR-0004](adr/0004-native-ollama-endpoint.md).
- **`futures = "0.3"` must be added** to `src-tauri/Cargo.toml`. rig does not re-export it, and consuming the stream needs `StreamExt::next()`.
- **`CompletionRequest::from(Vec<Message>)`** is how to pass a whole conversation. The `.messages()` setter *inserts* before the prompt rather than replacing it.
- **Empty user or assistant messages are rejected** by rig at send time, with `ProviderError::Request`.
- **Ollama ignores `tool_choice`**, and rejects `Effort::Minimal`, `Effort::XHigh` and `Reasoning::Budget` outright.
- **`@mui/x-chat-headless` is not resolvable** under pnpm's strict layout — import it as `@mui/x-chat/headless`.
- **`ChatMessage` is two different things**: the component from the package root, the entity type from `/headless`. Alias one of them.
- **`@mui/x-chat` 9.0.0-alpha.22 has no `ChatLog`, `Composer` subpath, or `messages` prop.** The integration point is `<ChatBox adapter={…} />`, and the `adapter` prop is required.
- **A `finish` chunk ends the whole stream, not one message.** The library's read loop breaks as soon as it sees one, and it renders one bubble per stream. A turn that needs two messages — one for the tool call and one for the answer — is silently truncated after the first. This is why a tool-using turn is one message with several parts.
- **`@mui/x-chat` renders markdown by default**, via `markdown-to-jsx`, repairing incomplete syntax mid-stream, and routes fenced code blocks to the themed `ChatCodeBlock`.
